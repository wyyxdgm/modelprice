Bottom line: the approach holds — but your phrasing mixes two different things. With the corrections below it becomes a rigorous, useful tool (this page).

1. "Sort by cost/task + drag the range's left edge" ≠ the winner by itself. A sort direction produces no conclusion; the real operation is: fix a threshold T and take the min-cost model among those with score ≥ T. Sweep T from the highest score down and the winner sequence is the lower envelope (Pareto frontier) of the (score, cost) plane. It can be proven that the map C(T) = min{cost : score ≥ T} is monotonically non-decreasing, so "every tier has a winner, and winners get pricier as the threshold rises" necessarily follows — your intuition is right. Arena's official /pareto view plots exactly this curve. The key correction: the winner only switches when a strictly cheaper model appears — not on every drag step — so the frontier is a staircase, and each flat segment is "the score range this model rules".

2. "Best value" has at least three definitions, with different answers:

  • Threshold (= your idea, and the only one correct as constrained optimization): min cost s.t. score ≥ T. Meaning: "cheapest among models that clear the bar".
  • Score per $: max score/cost. Meaning: "cheapest per point" — but Arena scores carry a ~1200 baseline offset that inflates the numerator, so this almost always picks the cheapest small model. Little practical value.
  • Excess score per $: max (score − baseline)/cost. Marginal value after removing the offset; good for comparing "pay more, gain how much" efficiency.

Closest to a purchasing decision is the marginal price: moving from the current tier up one, Δcost / Δscore = dollars per extra point. The tier table computes it for you.

3. Five pitfalls that flip conclusions (each has a toggle in the tool):

  1. Overlapping confidence intervals. If the score range is narrower than the CI, rankings inside it are noise. Example: on the HTML board, Inkling 2 Small has only 130 votes (CI ±55); Muse Spark Open ±41. This tool offers a "strict mode": only accepts a gap where A's CI lower bound > B's CI upper bound; statistically indistinguishable adjacent tiers are merged into one (keeping the cheaper model).
  2. Preliminary / low votes. Don't crown a "value champion" from a model with <1000 votes.
  3. Cost/Task (P50) is a workload-mix artifact. The same model can have different costs on different boards (Overall / Frontend / Fullstack / HTML / React) because task length and tool-call depth differ. P50 also ignores the tail: when an agent goes off the rails, P95 can be 5–10× P50. And it only covers token spend — not latency, retry rates, or context-window limits.
  4. Dataset truncation. In this scrape, frontend_os and overall_all only cover the high-score segment (the low tail wasn't fully scraped). Good news: the high-score end of the Pareto frontier is unaffected by missing low-scoring models (a lower-scoring, pricier model can never enter the frontier); bad news: the global cheapest price and the "excess score/$" baseline skew. Use the paste box at the bottom to fill the gap.
  5. Point-in-time. The official API returns 403, so only page snapshots are possible; prices and ranks change weekly. CSV exports carry the date in the filename.

4. The question you actually want, and where it lives in the tool: "on a given board, within an acceptable score range, which model has the best value" → that's Threshold mode + the score-range slider: set lo to your minimum acceptable capability and hi to the ceiling you won't pay extra for; the card gives the answer, and the step chart tells you "how much more the next tier costs" — more decision-useful than a single champion.

5. One counter-intuitive but important reminder: models on the Pareto frontier are mutually undominated; there is no "best one on the frontier". "Best" depends on your utility function — how fast your marginal utility of score decays, and your budget. So the right question is not "which has the best value" but "above the minimum score I can accept, how many points does each extra dollar buy — and from which tier does that exchange rate stop being worth it". The "marginal cost $/pt" column in the tier table is exactly that exchange-rate curve; find its knee.

6. Price is a function of time — this version makes "the hour" a first-class variable. The board's Price $/M is a snapshot of list price at scrape time, and list prices change over time. Two time dependencies are verified:

  • Intraday rhythm (peak/off-peak). DeepSeek peak = weekdays 01:00–04:00 and 06:00–10:00 UTC; all other hours (including the whole weekend) are half price. The annoyance: the board mixes both conventions in one table — V4.1-Flash-20261017 is listed at off-peak $0.15/$0.60, while V4.1-Flash-20260910 and the V4-Pro family are listed at peak $0.30/$1.20 and $1.32/$3.96. Comparing across rows means comparing one model's peak against another's off-peak.
  • Calendar events (promo expiry). The 11-11 snapshot listed GLM-5.3-Flash at a launch promo ($0.05/$0.18) that had already ended 2026-09-09 ($0.15/$0.50 real, ~2.9×) — the tool corrected it. The 11-20 snapshot lists $0.02/$0.07 (below the post-promo price; likely a new promo), so the correction no longer matches and the rule was retired on 2026-11-22. Each correction is matched against the exact listed price; when the board moves on, the rule drops out instead of distorting the cost.

Conversion: Cost/Task = token usage × unit price; usage doesn't change with price, so the correction = scale by the weighted unit-price ratio: scale = [pin'·(1−w) + pout'·w] ÷ [pin·(1−w) + pout·w], where w = output token share, default 8% (from the Agent board: median inferred input/output ratio ≈ 11:1 across 14 models; range 3.8–17.9×; adjustable via slider). DeepSeek's peak/off-peak moves input and output proportionally, so it is insensitive to w; w only matters for corrections that shift input and output by different factors.

Losslessly reversible: every model keeps cRaw (the raw board value); all scenarios are derived from it, and switching toggles off restores it exactly — no "edits drifting from truth".

Conclusions actually change with the hour — that's the point: off-peak, DeepSeek's older version is half price and kicks Hy3 and MiMo-V2.5 off the Pareto frontier (fully dominated); the T=1500 winner changes from Hy3 $0.04 to DeepSeek-V4.1-Flash-20260910 $0.03; conversely at peak, 20261017 rises from $0.12 to $0.24. Chart ③ draws this as a 168-hour weekly C(T) curve: gray bands are peak windows; jumps in the line are champion changes.

Three limits of this section: ① scores are a 2026-11-11 snapshot and don't change with time, so the time axis reflects the time-dependence of prices, not of capability (capability also drifts as boards update); ② board costs use P50 usage and exclude cache-hit discounts (DeepSeek cache input: peak $0.006 / off-peak $0.003; Anthropic cache input $0.10–$1.00), so real agent bills can be well below "usage × list price"; ③ two uncertain rules (whether V4-Flash also splits peak/off-peak; Mistral Medium 3.5 and GPT-6 Sol being 2× off vs a third-party index) are off by default — tick them only for sensitivity analysis. The rule table PRICE_EVENTS lives in the source, free to edit — it's just "model name → unit price at two hours". One of them, gem_dec1, is a future event: Gemini 4 Carbon/Argon have announced a hike from $2/$10 to $4/$20 on 2026-12-01 (cache price $0.10→$0.20); drag the pricing date into December and you'll see it drop off the overall_all frontier that day, replaced by GPT-6.1 Sol.

7. Cache hit rate — the single most impactful variable (default 95%). Arena's Cost/Task is computed at cache-miss prices, so for agent workloads — where prefixes get re-read constantly — it's a systematic overestimate. Cache discounts only apply to input tokens; output is always full price: effective input price = (1−h)·input price·write multiplier + h·input price·cache ratio, where h is the hit rate. Two easily-missed details: ① cache read prices are stored as a ratio of the input price, not absolute values, so peak/off-peak, promo expiry and future hikes move cache prices automatically (DeepSeek peak $0.006 → off-peak automatically $0.003); ② write multiplier: Anthropic (5-min tier) and OpenAI (30-min tier) bill cache writes separately at 1.25× input price, and the missed share is paid at the write price, so at the same 95% hit rate Claude's discount is thinner than DeepSeek's; DeepSeek / Z.ai / Xiaomi / Tencent / Google (implicit cache) / xAI don't charge a write fee. 39 models use published ratios (DeepSeek 2%–3.3%, MiMo 0.8%–2%, Kimi 10%–20%, GLM 18.3%–20%, Hy3 25%, Grok 25%, Anthropic 2.5%–10%, OpenAI 5%–10%, Gemini 5%, Mistral Large 4 10.3%); the other 48 have no published price → estimated at an industry-typical 10% and labeled "est." in the UI, or flatten everything with "Flat 10%" for a conservative comparison. Cache price sources: DeepSeek's official pricing page; Anthropic / OpenAI / Google / xAI / Moonshot / Z.ai pricing pages (cross-checked via benchlm.ai, morphllm, sentra.app, maximem.ai, tech-insider, felloai, eesel, layer3labs, getnadir, imisofts, munderdiffl.in, datastudios.org, aipricing.guru, glm-ai.chat, glm5.app, subconscious.dev, mem0.ai, llm-stats, orcarouter, requesty.ai, codersera, saascity, alphasignal, truescho, flowtivity, deepseekai.guide); the full comparison table is in the README.

Three conclusion-level changes cache discounts bring: ① levels: top models generally save 59%–79% (Fable 5.2 $11.04→$4.10, Kimi $0.91→$0.375, MiMo-V2.6-Flash $0.05→$0.011); ② frontier structure: overall_os goes from 7 tiers to 8, with three DeepSeek variants squeezing in; ③ scheduling value gets compressed: the weekly cost amplitude at T=1600 shrinks from 1.67× to 1.11× — with cache at 95%, dodging peak hours only saves ~10% more, so the right order is fix prefix caching first, then talk scheduling. Also, the "output share" slider goes from irrelevant to the second-most sensitive parameter once cache is on: at the same 95% hit rate, DeepSeek-20261017 saves 86% at w=2%, 68% at w=8% (default), 55% at w=15%, 40% at w=25%, and only 25% at w=40% — the longer your outputs, the less cache can rescue. Conversely, if a tier champion's input and output prices both double (like DeepSeek-20261017 at T=1664), cache can't compress the amplitude — still 2.00× — and that tier's lever is scheduling.
